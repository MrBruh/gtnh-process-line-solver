# Dev-toolchain pins, so a fresh clone and a CI run check the same code the same way.
#
# WHY THIS EXISTS. `pip install -e ".[dev]"` floats to whatever is newest that day, and the
# floors in pyproject are floors, not pins. mypy crossed a major and pytest reached 9.x with
# nothing in the repo recording it, which is the failure mode this file closes: a red CI run
# that no commit caused, or worse, a green one that should not have been.
#
# WHY A CONSTRAINTS FILE AND NOT A FULL FREEZE. A `pip freeze` lockfile is resolved for one
# interpreter on one OS; this project's CI spans Python 3.10 and 3.14 on Linux while most
# development happens on Windows, so a freeze would pin wheels that do not exist on half the
# matrix. A constraints file only bounds what actually gets installed, never forces it, so it
# stays correct across the whole matrix.
#
# WHY THESE PACKAGES AND NOT EVERY TRANSITIVE DEP. These are the ones whose version alone can
# turn CI red or green without a line of this repo changing: the linters and type checker decide
# what passes static analysis, the test stack decides what runs and how coverage is measured, and
# pydantic decides what the IR contracts accept. Pinning the long tail beneath them would buy
# little and break on the matrix for the reason above.
#
# The pyproject `[dev]` floors stay loose on purpose - they are library metadata, stating the
# minimum this project works with. This file is the single place an exact version is chosen.
#
# TO UPDATE: bump the pin here, and if it is ruff, bump `.pre-commit-config.yaml` to the matching
# rev in the same commit. Those two are checked against each other by
# `tests/test_toolchain_pins.py`, because a hook that formats with a different ruff than
# `ruff format .` produces a diff no one asked for. Dependabot's pip and pre-commit ecosystems
# propose both halves; the test is what stops one landing without the other.
