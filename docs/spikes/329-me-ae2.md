# Spike: the AE2 rules ME support rests on (epic #329)

**Status:** research only, nothing implemented. Every later ME pull request (#331 to #339) builds
on the facts below and cites them by section. Read this before touching `dataset/me.py`,
`router/me.py`, `validator/me.py` or the AE2 parts of the previewer and the exporter.

**Why a spike.** ME support adds a second validator gate, and that gate re-implements AE2's channel
assignment. A wrong rule there does not fail loudly: it certifies an ME network in which a bus never
gets its channel, or a line the network cannot keep fed. So every rule is read from source first.

## 0. What changes the plan

The plan on #329 was written from an earlier pass over the same sources. Reading them closely
changed these, each argued in its section:

1. **An ME interface takes everything a GT machine pushes into it, straight into the network.**
   This AE2 build gives the interface a GTNHLib item-sink capability, and every GT item mover uses
   GTNHLib's transfer, so a pushed stack is injected in the same call; FC's dual interface does the
   same for fluid. Neither caps the rate: **the pusher does** (section 4.5). The interface is the
   right ME device for any output GT pushes, and its rate check is the pusher's rate.
2. **FC's "fluid interface" is the ME Dual Interface, and it takes items too** (section 4.6). One
   dual interface part on a single block's output face takes both its item and its fluid
   auto-output, so a single block whose items and fluids both ride one ME network needs no import
   bus for the second commodity.
3. **A multiblock's normal output bus and output hatch push into whatever faces their front**:
   a bus every 8 ticks, a hatch its whole tank every tick (section 4.8). So with the GT ME hatch
   policy at `never`, an output is a normal hatch with an interface part in front of it, and needs
   no cards.
4. **Channels on a tree are exact and order-free.** "Every node's downstream channel-device count
   is at most its capacity" is necessary and sufficient when the AE graph is a tree, and how many
   devices get a channel does not depend on AE's visiting order (section 2.4). With cycles, AE's
   choice of spanning tree can depend on hash and history order, so the validator needs a sound
   over-approximation there or must refuse cycles (section 2.5).
5. **An ad-hoc network ignores cable capacity entirely.** It counts channel devices grid-wide: 8 or
   fewer all work, on any cable, and a 9th takes every channel away (section 2.6).
6. **Channel power is not `channels / 128`.** It is the channels passing through every node *and*
   every connection, summed, over 128: roughly channels times hops, twice (section 6.2).
7. **Super Speed cards are craftable, behind LuV.** Superluminal is behind UV and does not fit FC's
   fluid buses (section 4.3).
8. **AE2's textures are CC BY-NC-SA 3.0**, not LGPL like its code (section 9.2). A preview HTML
   that embeds them redistributes them, which the previewer work has to settle before it draws any.
9. **The Schematica printer cannot build an AE2 cable.** A cable bus keeps all of its geometry in
   tile-entity NBT, and the printer applies none (section 7.1). An exported AE2 network shows in the
   hologram only.
10. **An energy acceptor has no amp cap.** It takes every whole amp its grid has room to store, so
    an empty network pulls its source's full output until 80,000 AE per acceptor are stored (the
    pack's multiplier scales buffers too). The cable to it must carry that, or sit behind a 1 A
    limit (section 6.3).
11. **GT's ME output bus is slower than a normal bus with an interface.** It flushes every 41 ticks,
    so 39 items/t sustained at its default 1,600, where a normal EV output bus pushes 200 items/t
    into an interface part on its front (sections 4.8, 5.3).

## 1. Channels: what each node can carry

### 1.1 Capacity belongs to a grid node

- `GridNode.CHANNEL_COUNT = { 0, 8, 32, Integer.MAX_VALUE }` (`appeng/me/GridNode.java:56`). The
  index (`:210-215`): 3 (unlimited) with channels off, 0 for `CANNOT_CARRY`, 2 (32) for
  `DENSE_CAPACITY`, else 1 (8). Read back by `getMaxChannels()` (`:569-571`).
- The pack has channels on: `B:Channels=true` (cfg:164, read as `Features.NetworkFeatures` at
  `appeng/core/AEConfig.java:326-334`).
- A connection has no capacity of its own (`appeng/me/GridConnection.java:159-167`). A cable
  cell, or a block device that passes channels, caps the total for its whole downstream subtree.
  Any non-cable node on a trunk (an energy acceptor, an interface block) caps everything beyond it
  at 8.

| Node | Flags | Carries |
|---|---|---|
| Glass, covered, smart cable | `PREFERRED` only (`appeng/parts/networking/PartCable.java:72`) | 8 |
| Dense smart, dense covered cable | `DENSE_CAPACITY` (`PartDenseCable.java:54`, `PartDenseCableCovered.java:53`); `setFlags` replaces, so no `PREFERRED` (`appeng/me/helpers/AENetworkProxy.java:306-312`) | 32 |
| Controller | `CANNOT_CARRY, DENSE_CAPACITY` (`appeng/tile/networking/TileController.java:55`) | none through it |
| Quartz fiber | `CANNOT_CARRY` (`appeng/parts/networking/PartQuartzFiber.java:56-58`) | 0 |
| Any other device | default | 8 |

There is no ultra-dense cable: `PartType` registers exactly five cables (`appeng/items/parts/PartType.java:71-110`);
the API's `partCableUltraDense*` fields are referenced by nothing.

### 1.2 Which devices spend a channel

`REQUIRE_CHANNEL`:

- every part extending `PartBasicState` (`appeng/parts/PartBasicState.java:43`): import, export and
  storage buses (`PartUpgradeable.java:27`, `PartSharedItemBus.java:48`, `PartBaseExportBus.java:41`,
  `PartStorageBus.java:100`), the interface part (`PartInterface.java:80`), P2P tunnels, emitters,
  planes; terminals through `AbstractPartDisplay` (`appeng/parts/reporting/AbstractPartDisplay.java:38`);
- the interface, block and part, through `appeng/helpers/DualityInterface.java:181`; FC's dual
  interface through `com/glodblock/github/util/DualityFluidInterface.java:85`; FC's buses extend
  AE2's (`com/glodblock/github/common/parts/PartFluidExportBus.java:26`);
- blocks: drive (`appeng/tile/storage/TileDrive.java:109`), ME chest, IO port, security, wireless,
  spatial, crafting tiles (one per CPU, `MULTIBLOCK`), super replenisher;
- every GT ME hatch (section 5).

No channel: cables, the energy acceptor and cells (no flags, `TileEnergyAcceptor.java:29`,
`TileEnergyCell.java:29`), the controller, quartz fiber, the toggle bus (`setFlags(PREFERRED)`
replaces the inherited `REQUIRE_CHANNEL`, `PartToggleBus.java:57-58`), the cable anchor (no grid
node, `PartCableAnchor.java:153-156`).

## 2. Pathing: how AE2 hands channels out

This fork does not use the old 1.7.10 pathing; it ports modern AE2's BFS plus DFS
(`appeng/me/pathfinding/PathingCalculation.java:31-40`).

### 2.1 The algorithm

```python
# max(n) = CHANNEL_COUNT[...] (1.1); cls(n) = 0 dense, 1 PREFERRED, 2 other; cls(connection) = 0
# conns(n) = GridNode.connections, a LinkedList (GridNode.java:58)

def pathing(grid):                                   # PathingCalculation
    visited, Q = set(), [deque(), deque(), deque()]  # :49-59
    def enqueue(item, qi):                           # :107-127
        visited.add(item)                            # marked when ENQUEUED
        Q[max(cls(item), qi)].append(item)           # :125, the index is sticky
    for ctrl in controllers(grid):                   # a HashSet: identity-hash order
        visited.add(ctrl)
        for c in conns(ctrl):
            if not is_controller(other(c, ctrl)):
                enqueue(c, 0); c.sideA = ctrl        # :85-104, every root in queue 0
    for qi in (0, 1, 2):                             # :129-137, each queue to exhaustion
        while Q[qi]:
            i = Q[qi].popleft()                      # FIFO
            for pi in options(i):                    # a node: conns(i) in list order
                if pi in visited: continue           # the first poller is the parent
                set_parent(pi, i)                    # GridNode.java:535-567
                if REQUIRE_CHANNEL(pi):
                    try_use_channel(pi)              # :139-176, decided NOW, never retried
                enqueue(pi, qi)
    dfs_post_order_counts()                          # :217-272, section 2.3

def try_use_channel(d):                              # :185-210
    if any(count(n) >= max(n) for n in path(d)):     # d up to just below the controller
        return False
    for n in path(d): count(n) += 1
    return True
```

- A device's channel is decided once, when it is discovered, along its single BFS path. AE never
  retries a starved device or balances load across paths.
- `try_use_channel` checks only the device and its `highestSimilarAncestor` chain, the top node of
  each run of equal `subtreeMaxChannels` (`GridNode.java:545-554`). Since `subtreeMaxChannels` never
  grows going down the tree, a non-top node's count is at most its run top's, and its capacity at
  least the top's; checking the tops is checking every node on the path. Controllers are never on
  the chain.
- A node whose parent is a controller is a root with its own capacity (`GridNode.java:539-543`):
  32 for a dense cable, 8 for a normal cable or a block device.
- `MULTIBLOCK` members share one channel (`:148-171`, `:268-271`); none of the devices this work
  places is one.

### 2.2 Controllers

- **A controller never carries channels.** It is visited first and never enqueued (`:85-104`).
  Every neighbour that is not a controller is a root; a node touching two controller faces is still
  one root with its own capacity.
- **No per-face or per-block limit** exists in code. One controller block can feed up to 6 x 32,
  one dense cable per face.
- **Per block** (`TileController.java:95-121`): a controller with colour-compatible controllers on
  both sides along two or more axes is invalid and drops all its sides.
- **Per cluster** (`appeng/me/cache/PathGridCache.java:176-204`, `appeng/me/pathfinding/ControllerValidator.java:39-61`):
  every controller in a grid must form one cluster joined by direct controller-to-controller
  adjacency, within 7 x 7 x 7 (`ControllerValidator.java:50`). Two controllers joined only through
  cable are `CONTROLLER_CONFLICT`, which gives every node 0 channels (`PathGridCache.java:95-98`).

### 2.3 Counts after pathing, and what a cable shows

- A post-order DFS from the roots (`PathingCalculation.java:217-266`) sets each node's
  `usedChannels` to the sum over its child connections plus its own grant (`GridNode.java:578-598`);
  a connection carries its child node's count (`GridConnection.java:169-176`). Non-tree connections
  carry 0.
- **Channel lights** (`appeng/parts/networking/PartCable.java:358-411`), per side: a connection whose
  ends are both `DENSE_CAPACITY` (the controller counts) shows `min(used, 32) / 4`, integer
  division, so 1 to 3 channels show nothing; any other shows `min(used, 8)`. A side holding a part
  shows that part's connection's count. Unpowered shows 0. The icons are in section 8.3.
- WAILA shows the largest count over the node's connections, its subtree total
  (`IUsedChannelProvider.java:17-41`).

### 2.4 On a tree the outcome is exact

Take a component of the AE graph, controllers removed, that is a tree with one node touching the
controller cluster. Every node then has exactly one possible parent, and with `D(n)` the channel
devices in `subtree(n)`, itself included:

- **sufficient:** if `D(n) <= max(n)` for every node, each device finds every count on its path
  below capacity when it is discovered, so every device gets a channel;
- **necessary:** if some `D(n) > max(n)`, at most `max(n)` channels exist inside `subtree(n)`, so a
  device there starves;
- **the number granted is order-free** (the constraints `|S n subtree(n)| <= max(n)` form a laminar
  matroid, and AE's exact check tried once per device yields a basis): `granted = sum over roots of
  r(root)`, `r(n) = min(max(n), own(n) + sum over children r(c))`. Only *which* device starves
  depends on order.

So a validator that rebuilds the graph and finds a tree can apply `D(n) <= max(n)` exactly, and
report an overflow as a number rather than a guess.

### 2.5 Cycles, and where AE's order is not fixed

- The **root order across controller blocks** follows a `HashSet` of nodes with identity hashes
  (`appeng/me/MachineSet.java:19`), so it varies between runs.
- **Each node's connection list** is a `LinkedList` appended as connections form
  (`GridNode.java:116-121`), which follows placement, tile-init and chunk-load order, and every
  repath moves a node's BFS parent to the front (`GridNode.java:560-566`). The last tree shapes the
  next.
- Repath is never incremental: any node or connection change sets a flag and the next grid tick
  recomputes from scratch (`PathGridCache.java:65-117`, `:308-312`).

AE builds one spanning tree; non-tree connections carry nothing, so a parallel path adds **no**
capacity. Derived from the FIFO and sticky-queue rules (not stated in the source): label each item by
the counts of path items, by queue, from its root; polling is lexicographic in `(c2, c1, c0)`; each
node's parent is an incident connection of minimal label. Therefore:

1. If no node has two incident connections tied at its minimal label, the tree is unique even with
   cycles, and 2.4 applies to it.
2. Otherwise a sound check is `D+(n) <= max(n)`, counting the devices reachable from `n` in the
   possible-parent DAG: every tree AE can pick has subtrees inside those.

A router that lays a tree and keeps it one (no foreign AE node touching it) never meets either case;
the validator still rebuilds the real graph, because AE cables connect to every compatible
neighbour on their own.

### 2.6 Ad-hoc networks (no controller)

- A grid with no controller node is ad hoc (`PathGridCache.java:180-181`). A network whose only
  controllers are invalid blocks is ad hoc too.
- It counts every channel device in the grid (`:208-243`): **8 or fewer all get a channel, on any
  cable kind; 9 or more and every one of them gets 0** (`:223-227`, `AdHocChannelUpdater.java:28-38`).
  No topology check runs at all; dense cable does not raise the limit.
- A P2P ME tunnel inside an ad-hoc grid with any P2P outer node also zeroes it (`:219-221`).

### 2.7 Hand traces (unit-test material)

**Controller, starved ninth bus.** All Fluix. Controller C at (0,0,0); dense D1, D2, D3 at
(1,0,0), (2,0,0), (3,0,0); smart S1, S2, S3 at (3,0,-1), (3,0,-2), (3,0,-3); export-bus parts on S1
(up, down, east, west), S2 (up, down, east, west) and S3 (up): nine buses.

- D1 is a root (32); D2 and D3 share its run. S1 is `min(32, 8) = 8`, a new run top, and the only
  item in queue 1.
- Polling S1 discovers S2 (queued) and S1's four buses, granted: S1 counts 4. FIFO polls S2 next:
  its four buses take S1 to 8. S3's bus then fails at `count(S1) = 8 >= 8`
  (`PathingCalculation.java:194-195`). **The S3 bus starves under any order.**
- Counts: buses on S1 and S2 1 each, S3's bus 0; S3 0, S2 4, S1 = D3 = D2 = D1 = 8; connections
  C-D1, D1-D2, D2-D3, D3-S1 8 each, S1-S2 4, S2-S3 0. Granted 8; channel power sum 44 + 44 = 88.
- Lights: dense-to-dense faces 8/4 = 2; D3/S1 8; S1/S2 4; S2/S3 0; each granted bus 1.

**Ad hoc.** Smart S1, S2, S3 in a line, no controller, four buses on S1 and four on S2: 8, all
granted. A ninth bus on S3: 9 > 8, all nine get 0.

## 3. Connections: which blocks join a network

- Only world nodes look for neighbours (`GridNode.java:364-366`), scanning down, up, north, south,
  west, east (`:371`). A connection needs both ends to accept it:
  `canConnect(node, f) && node.canConnect(this, f.opposite)` (`:379`), each checking its valid
  sides and the colour (`:448-457`).
- **Colour:** `AEColor.matches` is `this == Transparent || other == Transparent || this == other`
  (`appeng/api/util/AEColor.java:121-123`). Transparent is Fluix. Colour alone keeps two adjacent
  networks apart.
- **Parts never touch neighbours.** A part's proxy is a world node only if it is a cable
  (`appeng/parts/AEBasePart.java:94-95`), so a bus or interface part joins only its own centre
  cable, by an internal connection (`appeng/parts/CableBusContainer.java:187-205`, `:488-517`).
  P2P tunnels, the toggle bus and quartz fiber have a second, outward node.
- **Any part on a side removes that side from its centre cable's connections**, a node-less cable
  anchor included (`CableBusContainer.java:459-475`). That is how an anchor blocks a connection.
- **Parts fit only on glass, covered or smart cable.** Dense cables report `DENSE_CABLE` support
  (`PartDenseCable.java:58-60`, `PartDenseCableCovered.java:57-59`); every part accepts only
  `CABLE` (`AEBasePart.java:515-518`) except the anchor (`PartCableAnchor.java:203-206`), enforced in
  `CableBusContainer.canAddPart` (`:111-148`). No FC part overrides it.
- **Block devices connect on all six sides** by default (`AENetworkProxy.java:69`): the drive, the
  acceptor, the controller (all or none). The interface block drops only its `pointAt` side, none
  by default (`appeng/tile/misc/TileInterface.java:79`, `:131-136`). Two block devices touching, or a
  block device touching another network's compatible cable, merge the networks.
- **A GT ME hatch connects only through its front** (section 5).

## 4. Throughput: what each device moves

### 4.1 The scheduler

- Default tick ranges (`appeng/core/settings/TickRates.java`, the pack config has the same,
  cfg:396-420): interface 5-120, import bus 5-40, export bus 5-60, storage bus 5-60.
- A device ticks when `currentTick - lastTick >= rate` (`appeng/me/cache/TickManagerCache.java:71-72`).
  After a call: `FASTER` -2, `SLOWER` +1, `IDLE` to max, `URGENT` to min, `SLEEP` off until woken
  (`:89-105`); clamped to the range (`appeng/me/cache/helpers/TickTracker.java:50-60`); a new device
  starts at the midpoint (`:41`).
- A bus returns `FASTER` when it moved something and `SLOWER` otherwise
  (`appeng/parts/automation/PartBaseImportBus.java:161`, `PartBaseExportBus.java:146`). **A bus with
  work on every call settles at one operation per 5 ticks**, from the midpoint in 9 calls (import)
  or 14 (export). Buses are not alertable.

### 4.2 Item import and export buses

Items per operation (`appeng/parts/automation/PartImportBus.java:84-108`, `PartExportBus.java:45-69`):

| cards | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| Acceleration | 1 | 8 | 32 | 64 | 96 |
| Super Speed, added | 0 | +16 | +128 | +1024 | +8192 |

- Four upgrade slots, one card each (`appeng/parts/automation/PartUpgradeable.java:34-41`); at most
  4 of each speed card and 2 Capacity (`appeng/core/Registration.java:646-658`). 4 Super Speed and
  no Acceleration is `1 + 8192` per operation.
- So a bus moves `per_operation / 5` items per tick: 19.2 with four Acceleration cards.
- The budget is shared by every config slot and capped by the AE power available
  (`PartBaseImportBus.java:121-144`, `PartBaseExportBus.java:77`, `:98-136`); an import pulls 64 at a
  time in a loop until it is spent (`PartImportBus.java:163`).
- Config slots: `min(1 + 4 x capacity, 9)` (`PartSharedItemBus.java:135-137`). An unconfigured import
  bus pulls anything (`PartBaseImportBus.java:147-153`); **an unconfigured export bus does nothing**
  (`PartBaseExportBus.java:104-116`), so every export bus is configured to its item.

**The Fuzzy Card, and an item at any damage (#353).** A plan names an item a recipe takes at any
damage with Forge's wildcard, `registry@32767` (`minecraft:log@32767`, a coke oven's logs).

- **Without the card a bus matches its config exactly**, damage included: an export bus pushes the
  config stack itself (`PartBaseExportBus.java:123`), an import bus takes only
  `Platform.isSameItemPrecise` matches (`PartImportBus.java:126-130`, `AdaptorIInventory.java:49`),
  and a storage bus partitions with a `PrecisePriorityList` (`PartStorageBus.java:715`). No real
  stack is at damage 32767, so a bus set to one moves nothing.
- **With it the bus takes AE2's fuzzy path**: the export bus `doFuzzy`
  (`PartBaseExportBus.java:120-121`, `PartExportBus.java:91-104`), which pushes whatever
  `ItemList.findFuzzy` finds in the network's storage (`NetworkInventoryHandler.java:517-538`); the
  import bus `removeSimilarItems`, matching by `Platform.isSameItemFuzzy`
  (`PartImportBus.java:120-125`, `Platform.java:1113-1174`); the storage bus a
  `FuzzyPriorityList`, which asks `findFuzzy` too (`PartStorageBus.java:708-711`).
- **What the fuzzy path matches.** `findFuzzy` (`ItemList.java:73-104`) expands a config item that
  has ore dictionary names to every item of those names, and matches each one registered at 32767
  at any damage (`findFuzzyDamage` with `ignoreMeta`, `AEItemStack.java:587-649`); any other config
  item at the durability range the mode gives a damageable item, and at its exact damage otherwise.
  `isSameItemFuzzy` agrees: a damageable item at any durability under `IGNORE_ALL`, else any item
  sharing an ore name, else the exact stack. So **AE2 reads 32767 as "any damage" through the ore
  dictionary, not by the number**: Forge registers the vanilla logs as `logWood` at the wildcard,
  so a log bus with the card moves every `logWood` item the network holds, other mods' logs
  included, which is what a recipe taking any log accepts. A wildcard item in no ore name that is
  not damageable is matched only at 32767, card or not; the solver cannot tell (it has no ore
  dictionary) and fits the card, the only thing that can work (section 11).
- **The mode.** `FuzzyMode` (`appeng/api/config/FuzzyMode.java`): `IGNORE_ALL` and five percentage
  breakpoints of durability. `IGNORE_ALL` is the one that ignores damage, and every item bus
  registers it as its default (`PartSharedItemBus.java:64`, `PartStorageBus.java:143`), so a fresh
  bus already writes `FUZZY_MODE` `IGNORE_ALL` (7.5); the ore path ignores the mode altogether.
- **Which buses take it**: the import, export and storage bus, **one each** (`Upgrades.FUZZY`,
  `Registration.java:644`, `:653`, `:762`). FC's fluid buses take none (`CommonProxy.java:191-201`
  registers no `FUZZY` for them) and need none: a fluid is matched by name and has no damage.
- **The card itself**: `ItemMultiMaterial` damage **29** (`MaterialType.CardFuzzy`,
  `appeng/items/materials/MaterialType.java:83`), named "Fuzzy Card" (`en_US.lang:981`). It takes
  one upgrade slot like any card: an item bus has four (`PartUpgradeable.java:39-41`), a storage
  bus five (`PartStorageBus.java:231-233`). So a carded item bus keeps **three slots** for its
  speed cards, and a wildcard port faster than three cards move (12.8 items/t without
  Hyper-Acceleration) is split across two buses, each with its own card; the solver never drops
  the card for speed, since a fast bus that matches nothing moves nothing.

### 4.3 Fluid buses (FC) and the cards

- mB per operation: 1000 base; Acceleration 1-4 gives 8000, 32000, 64000, 96000; Super Speed
  **multiplies** that by 32, 512, 6144, 49152 (switch fall-through,
  `com/glodblock/github/common/parts/PartFluidImportBus.java:57-80`, `PartFluidExportBus.java:43-66`).
  Four Acceleration cards move 19200 mB/t.
- Cards (`com/glodblock/github/proxy/CommonProxy.java:191-201`): Acceleration 4, Super Speed 4,
  Capacity 2, Redstone 1, Crafting 1 (export). **No Superluminal**: it is not registered for them.
- The fluid buses exist while FC's `fluidIOBus` is on (`com/glodblock/github/common/Config.java:44-48`);
  the pack has it on (`config/ae2fc.cfg:16`).
- **Card recipes** (NHCore `src/main/java/com/dreammaster/scripts/ScriptAppliedEnergistics2.java`):
  - Super Speed (`ItemMultiMaterial` 56) is shapeless (`:196-202`): Advanced Card, Engineering
    Processor, Mysterious Crystal and an **Elite World Accelerator**, which is LuV
    (`gregtech/loaders/preload/LoaderMetaTileEntities.java:2057-2062`).
  - Superluminal (67) needs an Ultimate Time Anomaly, UV (`:2076-2082`; `LoaderMetaTileEntities.java:2069-2074`).
  - Both use the always-on `AEFeature.Core` (`appeng/items/materials/MaterialType.java:138-141`,
    `appeng/core/features/AEFeature.java:18-24`); no pack toggle disables them.

### 4.4 Storage bus

- Passive: its tick only watches the target for changes (`appeng/parts/misc/PartStorageBus.java:524-543`);
  inserts and extractions happen when the network asks, with no rate of its own.
- **Partition restricts insertion always, extraction only with the extract filter on** (Access
  `READ`, or `READ_WRITE` with Extraction `STRICT`; `PartStorageBus.java:677-683`,
  `appeng/me/storage/MEInventoryHandler.java:101-122`). The defaults are `READ_WRITE` and `LOOSE`
  (`PartStorageBus.java:141-142`), so by default the network sees everything in the target and only
  inserts are partitioned.
- **A GT Super Chest works natively from any face**: GT registers `AE2DigitalChestHandler`
  (`gregtech/crossmod/ae2/AE2Compat.java:77`), and the chest is an `IMEMonitor`
  (`gregtech/common/tileentities/storage/MTEDigitalChestBase.java:70-71`).
- **A GT Super Tank** has no GT handler; FC's fluid storage bus falls back to a polled
  `IFluidHandler` monitor at the storage bus's 5-60 ticks
  (`appeng/core/features/registries/ExternalStorageRegistry.java:59-74`,
  `appeng/me/storage/MEMonitorIFluidHandler.java:41`, `:157`). Its front face refuses fills unless
  input from the output side is on (`MTEDigitalTankBase.java:483-485`).

### 4.5 The ME Interface (part and block): no rate cap on a GT push

- 9 config and 9 storage slots of at most 64 (`appeng/helpers/DualityInterface.java:142-156`,
  `appeng/tile/inventory/AppEngInternalInventory.java:39-41`). It never pushes stocked items into
  neighbours, only crafting output (`DualityInterface.java:702-705`).
- **A GT push goes straight into the network.** GT's movers (`MTEBasicMachine`, the output bus,
  item pipes, buffers, conveyor covers) all use GTNHLib's `ItemTransfer`
  (`gregtech/api/util/GTItemTransfer.java:27-33`), which asks the target for an item sink capability
  before any inventory (GTNHLib `src/main/java/com/gtnewhorizon/gtnhlib/util/ItemUtil.java:146-164`).
  The cable bus answers with the part on that face (`appeng/tile/networking/TileCableBus.java:328-339`),
  and the interface part answers with `MEItemIO` (`appeng/parts/misc/PartInterface.java:431-446`;
  the block at `TileInterface.java:371-385`), whose `store` is a powered insert into the network
  (`appeng/capabilities/MEItemIO.java:57-85`). Only a rejected remainder lands in the 9 slots.
- So the interface's rate is whatever pushes into it. The 9-slot buffer (`9 x 64 / 5` = 115 items/t,
  draining on `URGENT`) matters only when the network refuses, or for a pusher that does not use
  GTNHLib.
- It needs its channel and an active grid; with no grid, `MEItemIO` is not built and GTNHLib falls
  back to the part's slots (`appeng/parts/layers/LayerISidedInventory.java:47-102`).

### 4.6 FC's dual interface: fluids pushed in go straight into the network

- In FC 1.5.106 the block `ae2fc:fluid_interface` and the part `ae2fc:part_fluid_interface` are both
  the **ME Dual Interface** (`com/glodblock/github/util/NameConst.java:15`, `:27`;
  `assets/ae2fc/lang/en_US.lang:3`, `:64`). There is no fluid-only interface.
- **Fluid:** GT pushes with `fill(side, <= 1000 mB)`; the cable bus routes `fill` to the part on that
  side (`appeng/parts/layers/LayerIFluidHandler.java:25-32`), and `DualityFluidInterface.fill`
  injects into the network's fluid inventory at once, with no tank, config or tick
  (`com/glodblock/github/util/DualityFluidInterface.java:520-536`). It refuses only when the grid is
  inactive or the network refuses the fluid. Its 6 tanks of 16000 mB (`:69-76`) are for stocking,
  not this path.
- **Items:** `PartFluidInterface extends PartInterface` and `TileFluidInterface extends TileInterface`
  without overriding the capability, so the dual interface is a full item interface too
  (`PartFluidInterface.java:55`, `TileFluidInterface.java:61`).
- AE2's plain interface part is not a fluid handler (`PartInterface.java:80-82`): a fluid needs the
  dual interface.

### 4.7 GT single-block machines

`gregtech/api/metatileentity/implementations/MTEBasicMachine.java`:

- **Items in** on any face but the main (working) face (`:994-1008`); the output face too while
  `mAllowInputFromOutputSide` is on, its default (`:131`). **Fluids in** likewise (`:361-363`).
- **Items out:** pulled from the output slots on any face but the main face (`:988-991`); **fluids
  out** from the output tank on any face but the main face (`:366-368`).
- **Auto-output** pushes through the output face (`mFacing`): items on recipe completion, when the
  inventory changes, while blocked every 300 ticks, and every 600 (`:657-670`), each output stack up
  to 64; fluids `drain(1000)` on the completion tick and every 20 ticks (`:642-655`). Both toggles
  default to **off** (`:131`, `:831-837`); a build sets them.
- **The fluid push is a GT-side rate limit**: at most 1000 mB per push, so `1000 x (1/D + 1/20)` mB/t
  for a recipe of D ticks. Fluid beyond that stays in the output tank and the machine stops starting
  recipes once an output would not fit (`:787-792`). This binds pipes as much as ME. A faster fluid
  output needs a fluid import bus, which drains the output tank from any non-main face
  (`PartFluidImportBus.java:97-128`; GT allows it on `isLiquidOutput`, `BaseMetaTileEntity.java:1914-1921`).
- **An export bus respects GT's face rules.** It tries only the slots the face exposes, gated by
  `canInsertItem` (GTNHLib `.../item/StandardInventoryIterator.java:36-48`), which reaches
  `allowPutStack`; on a main face nothing moves and no error is raised, the bus just backs off.

### 4.8 A multiblock's normal hatches with AE2 parts

- **Output bus:** pushes its contents into what faces its front every 8 ticks, unconditionally
  (`gregtech/api/metatileentity/implementations/MTEHatchOutputBus.java:224-261`), up to
  `(tier + 1)^2` stacks of 64: **`8 x (tier + 1)^2` items/t** (LV 32, MV 72, HV 128, EV 200).
  Pulled only through its front (`:229-232`).
- **Output hatch:** pushes its whole tank into what faces its front every tick
  (`MTEHatchOutput.java:131-144`); drained from any face (`MetaTileEntity.java:516-518`). No
  practical cap.
- **Input bus:** takes inserts **only through its front**, never into the circuit slot
  (`MTEHatchInputBus.java:253-258`); `(tier + 1)^2` slots plus the circuit (`:71`, `:83`).
- **Input hatch:** filled from any face (`MetaTileEntity.java:511-513`), one fluid, `8000 x 2^tier` mB
  (`MTEHatchInput.java:210-212`).

So a normal hatch's AE2 device sits on the cable cell its front faces, exactly where a pipe docks
today: an interface part for an output (no cards), an export bus for an item input, a fluid export
bus for a fluid input.

### 5.2 How they connect

- **Front face only.** The proxy's valid sides are `EnumSet.of(getFrontFacing())`
  (`gregtech/common/tileentities/machines/outputme/base/MTEHatchOutputMEBase.java:217-226`;
  `MTEHatchInputBusME.java:219-225`; `MTEHatchInputME.java:496-502`). A wire-cutter click sets
  `additionalConnection` and opens all six (`MTEHatchOutputMEBase.java:209-215`); a build and an
  export keep it off, so a hatch is always a leaf.
- **One channel each** (`REQUIRE_CHANNEL` only: `MTEHatchOutputMEBase.java:141-149`,
  `MTEHatchInputBusME.java:253-269`, `MTEHatchInputME.java:530-545`): no `DENSE`, `PREFERRED` or
  `MULTIBLOCK`, so two on one machine are two channels.
- **Colour is its GT paint**: unpainted is Fluix; dye `d` is `AEColor.values()[15 - d]`
  (`MTEHatchOutputMEBase.java:661-673`, `gregtech/api/enums/Dyes.java:143-146`).
- AE reaches it through `BaseMetaTileEntity`, which is `IGridProxyable`
  (`gregtech/api/metatileentity/BaseMetaTileEntity.java:94`, `:2201-2224`). A plain GT machine
  returns a null proxy (`MetaTileEntity.java:706-712`), so **a single block has no ME option of its
  own**, and GT has no ME cover (the only AE cover, `CoverFacadeAE`, is cosmetic). A single block
  reaches ME through AE2 parts alone.
- It reports no cable type on any side (`isOutputFacing` is never true for a hatch,
  `MetaTileEntity.java:394-396`), so the cable facing it draws a device plug (8.1).

### 5.3 Output bus and hatch (ME): the flush

- The hatch's own tick flushes when `tickCounter > lastOutputTick + 40`, independent of the
  controller (`MTEHatchOutputMEBase.java:469-486`): **41 ticks under continuous load**, and the first
  flush after an idle spell at once (`:494`, `:506`).
- A flush is a powered insert of the whole cache into network storage (`:499-504`): 10 AE per item,
  so a full 1,600-item flush costs 16,000 AE in one tick. What power or storage refuses stays
  cached.
- **Capacity is a soft gate**: by default a batch is accepted whole whenever the cache is under
  capacity (`:552-570`; `MTEHatchOutputBusME.java:234-253`). Sustained, it is the table's
  `capacity / 41`; a single large parallel batch is never refused for size. A storage cell inside
  raises the capacity (`:405-421`); a default build has none.
- It flushes only while its proxy is active: a channel, a powered network, not booting (`:494`,
  `appeng/me/GridNode.java:297-305`).

### 5.4 Stocking input bus and hatch (ME)

- **It holds nothing.** At recipe start each of its 16 slots simulates an extraction of up to
  `Integer.MAX_VALUE` from network storage (`MTEHatchInputBusME.java:812-832`); after the recipe
  check it extracts what was used, powered (`:760-802`). A short or unpowered extraction stops the
  machine with `stocking_bus_fail_extraction` (`:793-796`). The fluid hatch is the same
  (`MTEHatchInputME.java:419-483`, `:632-653`).
- So it draws from whatever the network's storage is: the player's main network when attached, the
  main network through a link storage bus, or the subnet's own chests. Its rate is that stock and
  that power.
- **16 types per hatch**, each configured (`SLOT_COUNT = 16`, `:93`); the basic one does not
  auto-pull. A recipe set needing more takes a second hatch.
- An inactive grid gives it no inputs (`:159-169`).

### 5.5 Where multiblocks take them

A structure check runs the hatch element's adder, which tests `instanceof` the parent class
(`gregtech/api/util/HatchElementBuilder.java:81-100`, `:525`, `:548`;
`gregtech/api/metatileentity/implementations/MTEMultiBlockBase.java:2361-2438`), so **every
multiblock takes an ME hatch wherever it takes the parent kind**. Known exceptions:

- the Tree Farm refuses a stocking bus (`gregtech/common/tileentities/machines/multi/MTETreeFarm.java:247-254`;
  GT++'s legacy one too);
- the Eye of Harmony refuses stocking buses and hatches (`tectech/.../MTEEyeOfHarmony.java:888-905`);
- the Forge of Gods requires exactly one Output Bus (ME) (`tectech/.../MTEForgeOfGods.java:313-319`);
- a distillation tower takes an ME output hatch per layer (`MTEMultiBlockBase.java:3194-3215`).

`previewer/textures.py`'s `HATCH_KIND_BY_CLASS` joins on an exact class name, so it resolves none of
these: they need their own map by mID.

## 6. Power

### 6.1 Units and draw

- Pack config: `D:UsageMultiplier=10.0` (cfg:375), `D:IC2=2.0` (cfg:370), read at
  `appeng/core/AEConfig.java:169-184`. `PowerUnits.EU.convertTo(AE, x) = x * 2.0 / 1.0`
  (`appeng/api/config/PowerUnits.java:50-52`): **1 EU = 2 AE**.
- Every tick the grid extracts its idle draw with the multiplier
  (`appeng/me/cache/EnergyGridCache.java:172-175`, `:203`, `:207-209`): **AE/t = (sum of idle +
  channel term) x 10**, which is **5 x that sum in EU/t**. A grid whose idle sum is 0 pays nothing.
- Moving costs `ceil(amount / unit) x 10` AE per insert or extract (`appeng/util/Platform.java:1307-1326`,
  `:1360-1390`): **10 AE per item, 10 AE per started 1000 mB** (`appeng/util/item/AEFluidStack.java:514-516`).
  A move power cannot cover is partial, not refused. FC's dual interface `fill` draws none (4.6).
- **The multiplier scales buffers too** (`appeng/tile/powersink/AERootPoweredTile.java:168-170`,
  `TileEnergyCell.java:193-195`): the controller and the acceptor each hold 80,000 AE, an energy
  cell 2,000,000.

| Device | Idle AE/t (before x10) | Source |
|---|---|---|
| Any node that sets nothing | 1.0 | `appeng/me/helpers/AENetworkProxy.java:60`, the only `IGridBlock`; nothing in AE2, FC or GT overrides it for the devices below |
| Import, export, storage bus; interface part and block; FC buses and dual interface; GT ME hatches | 1.0 | the default above |
| Cables, quartz fiber, toggle bus | 0 | `PartCable.java:73`, `PartQuartzFiber.java:55-58`, `PartToggleBus.java:55-56` |
| Energy acceptor, energy cells | 0 | `TileEnergyAcceptor.java:35`, `TileEnergyCell.java:37` |
| Controller, per block | 3 | `TileController.java:54` |
| ME drive | 2 plus its cells (1k 0.5, 4k 1, 16k 1.5, 64k 2) | `TileDrive.java:309-339`, `appeng/items/AEBaseCell.java:79-91` |

### 6.2 What channels cost

`channelPowerUsage = channelsByBlocks / 128.0` AE/t (`appeng/me/cache/PathGridCache.java:110`), added
to the idle draw (`appeng/me/cache/EnergyGridCache.java:207-209`):

- with a controller, `channelsByBlocks` sums the channels passing through **every node and every
  connection** the DFS visits (`PathingCalculation.java:246-254`): about twice channels x hops. The
  section 2.7 trace is 88, so 0.6875 AE/t before the multiplier;
- ad hoc, it is `nodes x channels in use` (`PathGridCache.java:89-92`).

### 6.3 Feeding a network: the acceptor, the controller and quartz fiber

- **The energy acceptor and the controller take GT EU** through `GTPowerSink`
  (`appeng/tile/powersink/GTPowerSink.java:11-54`), the pack's only EU path (`S:GregTech=AUTO`,
  `S:IndustrialCraft2=OFF`, cfg:312-314). Every side accepts, with **no voltage check** and **no amp
  cap**: `injectEnergyUnits(side, V, A)` accepts every whole amp that fits in the **grid's** free
  storage (`:19-34`; the acceptor funnels into the grid, `TileEnergyAcceptor.java:62-84`).
- A GT cable connects to them, electrically and visibly (`gregtech/api/metatileentity/implementations/MTECable.java:634-642`,
  `gregtech/api/graphs/GenerateNodeMapPower.java:50-55`).
- **So an empty network pulls every amp its source offers until its storage is full**: 80,000 AE per
  acceptor or controller, more with cells. The cable to an acceptor carries that inrush, not the
  network's steady draw, and a GT cable over its amperage burns. An acceptor needs either its cable
  sized for the source's full output or a 1 A limit in front of it.
- **Quartz fiber shares power between two grids without merging them** (`PartQuartzFiber.java:43-58`,
  `:117-126`, `:144-238`): two nodes, `CANNOT_CARRY`, idle 0, registered as an energy provider
  (`EnergyGridCache.java:561-565`). A subnet with no power of its own runs entirely through one.
- **A grid with no provider has a 1,000 AE buffer** (`EnergyGridCache.java:478-480`). One full Output
  Bus (ME) flush costs 16,000 AE (5.3), so a network with ME output hatches needs real storage: a
  controller, an acceptor, a cell, or a fiber to a network that has them.
- The powered flag goes true only after more than 30 ticks of continuous power (`:191`).

Orientation is AE2's placement rule (`appeng/block/AEBaseItemBlock.java:104-121`): `up` is `UP` and
`forward` the horizontal facing toward the player who placed it, so `NORTH` is a block placed
looking south.

**The cable bus.** Every ItemStack is `{id: Short, Count: Byte 1, Damage: Short}`, `id` the world's.
Cables are `ItemMultiPart` at the damages of 7.3 (Fluix dense smart 76, smart 56, covered 36, glass
16; Orange smart 41, Green smart 53). `extra:6` is `{}` on every cable. Per part, besides its
inventories:

| Part (item, damage) | `extra:N` settings |
|---|---|
| Import Bus (`ItemMultiPart` 240), FC Fluid Import Bus (`ae2fc:part_fluid_import` 0) | `filter` `""`, `FUZZY_MODE` `IGNORE_ALL`, `REDSTONE_CONTROLLED` `IGNORE` |
| Export Bus (260), FC Fluid Export Bus (`ae2fc:part_fluid_export` 0) | as import, plus `SCHEDULING_MODE` `DEFAULT`, `CRAFT_ONLY` `NO`, `nextSlot` Int 0 |
| Storage Bus (220), FC Fluid Storage Bus (`ae2fc:part_fluid_storage_bus` 0) | `filter` `""`, `FUZZY_MODE` `IGNORE_ALL`, `ACCESS` `READ_WRITE`, `EXTRACTION_MODE` `LOOSE`, `STORAGE_FILTER` `EXTRACTABLE_ONLY`, `STICKY_MODE` `NO`, `priority` Int 0, `filterCache` `{}` |

Those are each class's registered defaults (`PartSharedItemBus.java:63-64`,
`PartBaseExportBus.java:53-54`, `PartStorageBus.java:141-145`), so a fresh part writes exactly
these. The inventories: `upgrades` holds the cards one a slot from `#0` (`ItemMultiMaterial`, the
export bus's Acceleration 30 in `#0` and Hyper-Acceleration 56 in `#1`); `config` holds the filter
or partition, an item as `{StackType: "item", id, Damage, Count: 0b, Cnt: 1L, Req: 0L, Craft: 0b}`
and a fluid as `{StackType: "fluid", FluidName, Count, Cnt, Req, Craft}`, with no `Damage` and no
world id. A fluid's `Cnt` is how the slot was filled, 1000 on the export bus and 1 on the storage
bus; no bus reads it (the export bus sets each stack's size from its own rate,
`PartBaseExportBus.java:278`). An item's `Damage` is matched exactly: 32767, Forge's "any damage",
is read as a wildcard only by the fuzzy lookup (`ItemList.java:88`, `:97`), which an export bus
uses only with a Fuzzy Card fitted (`PartBaseExportBus.java:120`).

**The Fuzzy Card and a wildcard filter (#353): from the source, not the golden.** A bus set to an
item at any damage is written with a Fuzzy Card, and nothing of it is pinned by a save; each tag is
the golden's own shape filled in from AE2's source (4.2):

- the card is one more `upgrades` slot, after the speed cards, as `{id: ItemMultiMaterial's,
  Count: 1b, Damage: 29s}`, the shape the golden's Acceleration and Hyper-Acceleration Cards have,
  at `MaterialType.CardFuzzy`'s damage;
- the filter is the golden's item `config` stack at `Damage` 32767s, the plan's wildcard as is.
  AE2 saves whatever stack a player sets (`AppEngInternalInventory`), and the card reads 32767 and
  any real log alike through the ore dictionary, so the wildcard is the faithful record;
- the bus's `FUZZY_MODE` stays `IGNORE_ALL`, which every bus in the golden already writes: it is
  each class's default, and the mode that ignores damage.

The next save (#354) should hold a bus with a Fuzzy Card and a filter at damage 32767, to pin both.

**Where it differs from 7.2 to 7.4.**

- **No `part` or `proxy` tag anywhere.** Schematica saves a tile entity by writing it, loading a
  fresh tile from that NBT and writing the fresh one (`NBTHelper.reloadTileEntity`,
  `CommonProxy.java:139`); the fresh part has no grid node yet, and `AENetworkProxy.writeToNBT`
  writes the node only when there is one. So every Schematica save of AE2 lacks them, and an export
  that omits them matches what Schematica itself writes.
- **An empty inventory is omitted, not written as `{}`**: `AppEngInternalInventory.writeToNBT`
  removes the tag (`:200-208`). An unconfigured bus has no `config`, a bus with no cards no
  `upgrades`; 7.2's table names the keys a bus *can* write.
- **The storage buses write `filterCache` `{}`**, a key 7.2 does not list.
- **`hasRedstone` is live state.** The GUI save has 2 (undecided) on every cable bus; the server
  save has 1 (NO) on three bus cells, which the server had checked. 2 is a fresh bus's value, as
  7.2 says to write.
- **A controller's `Data` is its live state**, 1 here because the network was online; a block
  placed by hand starts at 0. The controller and the acceptor also write `inv` `{}` and
  `internalCurrentPower`, which 7.4 does not list.
- **A GT ME hatch's paint is GT's own, dye plus one.** `mColor` 0 is unpainted (Fluix to AE), and
  `mColor` 1 is dye 0, black, which AE reads as `AEColor` 15 (`Dyes.transformDyeIndex`, 5.2): AE
  colour `c` is `mColor` `16 - c`. The ME hatch otherwise saves as GT writes any machine, `mID`
  2718 and `mFacing` 0 onto the cable, plus its own settings (`autoStock`, `slots`, `refreshTime`,
  `additionalConnection` 0, ...).

**The two saves agree** on every AE2 tag but `hasRedstone` and the controller's
`internalCurrentPower`, which is what a GUI save of live state predicts (`docs/DOMAIN.md`,
Platform); GT's tiles differ the same way (stored energy, the Super Chest's count).
